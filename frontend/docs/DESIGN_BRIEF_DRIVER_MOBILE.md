# 디자인 지시서 — 기사용 모바일 앱 (MVP)

> **용도**: 이 문서를 그대로 디자인 작업 (Claude 등)에 전달한다. 읽는 사람이 이 프로젝트를 모른다고 가정하고 썼다.
> **범위**: MVP의 **모바일 앱 = 운전기사 화면**. 관리자 화면은 데스크톱 웹이라 별도 지시서로 다룬다.
> **작성일**: 2026-07-28 · 근거: `backend/docs/MVP_API_SPEC.md`, `MVP_RELEASE_TRACKER.md` §0, 실제 API 응답 대조

---

## 1. 요청 사항 (산출물)

아래 **7개 화면**의 모바일 UI를 디자인한다.

1. 로그인
2. 운행 시작 (운행 전 대기)
3. 오늘의 노선 (지도 + 정차 순서)
4. 승하차 기록 ← **가장 중요**
5. 운행 종료 (차내 잔류 확인)
6. 알림함
7. 공통: 로딩 / 빈 상태 / 에러 / 오프라인

**형식**: 화면별 레이아웃 + 주요 컴포넌트 명세 + 상태 변화 (빈/로딩/에러/성공). 라이트·다크 두 벌. **해상도 기준**: 세로 고정, 폭 360–430dp (실제 구현은 720dp 미만을 모바일로
본다).

---

## 2. 제품 한 줄

**학원 통학버스 기사가 운행 중 학생의 승하차를 기록하고, 오늘 돌아야 할 노선을 확인하는 앱.**

---

## 3. ⚠️ 사용 맥락 — 디자인을 지배하는 조건

이 앱은 **책상이 아니라 운전석에서** 쓰인다. 아래 조건이 미적 완성도보다 우선한다.

| 조건                            | 디자인 요구                                                                             |
|---------------------------------|-----------------------------------------------------------------------------------------|
| **정차 시간이 30초 남짓**       | 학생 1명 처리에 **탭 1회**. 확인 다이얼로그를 기본으로 두지 않는다                      |
| **운전 중 잠깐 본다**           | 한 화면에서 "지금 뭘 해야 하는지"가 **1초 안에** 읽혀야 한다                            |
| **한 손 조작 · 흔들리는 차 안** | 주요 버튼은 화면 **하단 절반**, 최소 터치 영역 **48×48dp**, 버튼 간 간격 넉넉히         |
| **장갑 착용 가능**              | 작은 아이콘 버튼만으로 기능을 숨기지 않는다                                             |
| **직사광선**                    | 명도 대비 높게. 회색 위 회색 금지. 상태는 **색만으로 구분하지 않고 아이콘·텍스트 병행** |
| **네트워크 불안정**             | 전송 중/실패/재시도 상태가 보여야 한다                                                  |
| **오조작이 사고로 이어짐**      | 되돌리기 어려운 동작(운행 종료)만 확인 단계를 둔다                                      |

**핵심 원칙**: 예쁜 화면보다 **틀리지 않는 화면**. 아이가 안 탔는데 탄 걸로 기록되면 안 된다.

## 4. 사용자 흐름 (실제 하루)

```
① 로그인
   ↓
② 운행 시작 화면 — 오늘 배정된 노선 확인 → [등원] 또는 [하원] 선택 → "운행 시작"
   ↓
③ 오늘의 노선 — 지도에 경로, 정차 순서 목록, 다음 정차까지 ETA
   ↓
④ 승하차 기록 — 정차마다 학생별 [승차]/[하차]/[인계완료] 기록   ← 하루 중 가장 오래 머무는 화면
   ↓ (반복)
⑤ 운행 종료 — 차내 잔류 학생 확인 후 종료
```

③④는 **하단 탭 2개**로 오간다 (지도 / 명단). ②⑤는 흐름 상 앞뒤에 붙는다.

## 5. 화면별 지시

### 5.1 로그인

- 요소: 로고/서비스명, 이메일, 비밀번호, 로그인 버튼
- 에러는 **서버 문구를 그대로** 보여준다 (예: "이메일 또는 비밀번호가 올바르지 않습니다")
- 개발 빌드에만 **"빠른 로그인"** 영역이 붙는다 (시드 계정 원터치 버튼 4개). 운영 빌드에는 없다 — 이 영역이 있을 때와 없을 때 레이아웃이 모두 자연스러워야 한다
- 회원가입·비밀번호 찾기는 **없다**(계정은 관리자가 생성)

### 5.2 운행 시작

운행 전 대기 화면. 기사가 하루를 여는 곳.

- **버스 정보**: 호차명 (`3호차`), 차량번호 (`서울12가3456`), 정원 (`25석`), 오늘 배정 인원
- **방향 선택**: `등원(PICKUP)` / `하원(DROPOFF)` — 두 개 중 하나를 크게 고르는 형태
- **큰 시작 버튼**: "운행 시작"
- 오늘 배포된 노선이 없으면: "배포된 노선이 없습니다. 관리자에게 문의하세요" 빈 상태

### 5.3 오늘의 노선 (지도 탭)

- **지도**: 경로 선 (polyline) + 정차 지점 마커 (번호 표시) + 현재 버스 위치
- **하단 시트**: 정차 순서 목록. 각 항목에 **순번 · 학생 이름 · 정류장/하차지 · 도착 예정 (ETA)**
- 진행 상태를 목록에 표시: 지난 정차 / **다음 정차 (강조)** / 남은 정차
- 상단 요약: 총 거리, 총 소요, 남은 정차 수
- ⚠️ ETA는 서버가 **초 단위 정수**(`etaSeconds`)로 준다 — "12분 후"처럼 사람이 읽는 형태로 변환해 보여줄 것

### 5.4 승하차 기록 (명단 탭) ★ 가장 중요

**하루 중 가장 오래 쓰는 화면이다. 여기 설계 품질이 앱 전체 품질이다.**

- 정차 단위로 묶인 학생 목록
- 학생 행: **이름 · 정류장 (또는 하차지) · 현재 상태**
- 상태는 3단계: `대기` → `승차 완료` → `하차 완료` → (하원이면) `보호자 인계 완료`
- 동작 버튼 **3종**:
    - **승차 (BOARD)** — 등원·하원 공통, 학생이 버스에 탐
    - **하차 (ALIGHT)** — 학생이 내림
    - **인계완료 (HANDOVER)** — 보호자에게 인계됨. **"하차 ≠ 인계"라 별도 단계다**
- 기록 즉시 학부모에게 알림이 발송된다 → **되돌리기가 사실상 불가능**. 그래서:
    - 버튼은 크되 **서로 충분히 떨어뜨린다**(오탭 방지)
    - 기록 후 상태가 **명확히 시각적으로 확정**돼야 한다 (체크 + 시각 표시)
    - 전송 중 상태를 보여준다 (낙관적 UI로 즉시 확정 표시하면 안 된다 — 실패 시 잘못된 안심을 준다)
- 필요한 표시: 정차별 진행률 (예: `3/5명`), 전체 탑승 인원
- **미승차 학생**은 눈에 띄어야 한다 (도착 10분 후 서버가 `NO_SHOW` 알림 발행)

### 5.5 운행 종료

**안전 기능이다.** 차내에 아이가 남은 채 운행이 끝나는 사고를 막는 화면.

- 정상: "탑승 학생 0명 · 전원 하차 완료" 확인 → "운행 종료" 버튼
- **차단 상태**: 아직 하차하지 않은 학생이 있으면 **종료가 막힌다**. 남은 학생 목록을 명확히 보여주고, 왜 종료할 수 없는지 설명한다
- 이 화면만 **확인 단계 (다이얼로그)** 를 둔다
- 종료 후 오늘 운행 요약 (총 거리·시간·처리 인원)을 보여주면 좋다

### 5.6 알림함

- 목록: 알림 유형 아이콘 · 내용 문구 · 시각
- 기사가 받는 유형: **근접 (APPROACH)**, **미승차 (NO_SHOW)**, **노선 배포 (ROUTE_PUBLISHED)**, 승하차 완료
- 새 알림은 실시간으로 위에 쌓인다 (WebSocket) → **새로 도착한 항목이 구분**돼야 한다
- 빈 상태: "받은 알림이 없습니다"

### 5.7 공통 상태

| 상태               | 요구                                                                                    |
|--------------------|-----------------------------------------------------------------------------------------|
| 로딩               | 화면 전체 스피너보다 **스켈레톤** 선호. 지도는 자리를 유지한 채 로딩                    |
| 빈 상태            | 아이콘 + 한 줄 설명 + (가능하면) 다음 행동 버튼                                         |
| 에러               | 서버 문구를 그대로 표시 + "다시 시도" 버튼                                              |
| 오프라인/연결 끊김 | 상단에 지속 배너. 앱을 못 쓰게 막지는 않는다                                            |
| 위치 보고 상태     | 기사 화면 어딘가에 **"위치 전송 중"** 표시가 필요하다(관리자가 버스를 보고 있다는 신호) |

## 6. 실제 데이터 — 이 필드만 존재한다

**디자인에 없는 데이터를 그리면 구현할 수 없다.** 서버가 실제로 주는 값은 아래가 전부다.

### 버스 (`GET /api/buses/me`)

```
name "3호차" · plateNumber "서울12가3456" · seatCapacity 25
onboard 3 (배정 인원) · overCapacity false · routeName "하원 A노선"
```

### 노선 (`GET /api/route-plans/driver/{busId}`)

```
direction PICKUP|DROPOFF · serviceDate · totalDistanceM 1566.0 · totalDurationS 397.0
polyline (경로 좌표)
stops[] = { seq 1, studentId 1, lat, lng, etaSeconds 0 }
```

### 운행 명단 (`GET /api/drive-sessions/{sessionId}/roster`)

```
{ studentId 1, name "김민준", location "정류장A", lat, lng }
```

### 승하차 기록 (`POST /api/ride-events`)

```
type BOARD | ALIGHT | HANDOVER · occurredAt · source MANUAL
```

### 알림 (WebSocket / `GET /api/notifications`)

```
type · message "김민준 학생이 승차했습니다" · createdAt
```

## 6.5 ★ 실제 테스트 데이터 (이 값으로 화면을 채울 것)

**시안에 가짜 이름·가짜 주소를 쓰지 말 것.** 아래는 Flyway 시드 (`V2__seed_data.sql`)로 DB에 실제로 들어 있는 값이며, **로컬에서 로그인하면 화면에 그대로 나타나는 데이터**다
(2026-07-28 DB 직접 조회로 확인).

### 로그인 계정 (비밀번호 전부 `password`)

| 이름         | 이메일                | 역할                            |
|--------------|-----------------------|---------------------------------|
| **박기사**   | `driver@school.com`   | 운전기사 ← **모바일 앱 사용자** |
| 한빛관리자   | `admin@school.com`    | 학원 관리자                     |
| 플랫폼관리자 | `platform@school.com` | 플랫폼 관리자 (소속 학원 없음)  |
| 김민준       | `student@school.com`  | 학생 (MVP 범위 밖)              |
| 이부모       | `parent@school.com`   | 학부모 (MVP 범위 밖)            |

### 박기사가 보는 버스

```
3호차 · 서울12가3456 · 25석
노선: 하원 A노선 (배정정원 25)
소속: 한빛학원
보험 만료: 2026-12-31
```

### 3호차 배정 학생 — **딱 3명이다** ⚠️

| 순 | 이름       | 승차 정류장 | 하차지            |
|----|------------|-------------|-------------------|
| 1  | **김민준** | 정류장 A    | 서울 서초구 자택  |
| 2  | **이서연** | 정류장 A    | 서울 서초구 자택2 |
| 3  | **박도윤** | 정류장 B    | 서울 강남구 자택  |

> **명단이 3명뿐이라는 점이 디자인에 중요하다.** 20 ~30명 리스트를 전제로 한 촘촘한 레이아웃을 만들면
> 실제 화면은 텅 비어 보인다. **3~5명 기준으로 자연스럽고, 25명까지 늘어나도 무너지지 않는** 구조여야 한다.
> (정원이 25석이므로 최대 25명까지 가능)

### 정차 지점

| 정류장   | 좌표              | 비고                  |
|----------|-------------------|-----------------------|
| 정류장 A | 37.5010, 127.0275 | 김민준·이서연         |
| 정류장 B | 37.5045, 127.0310 | 박도윤                |
| 학원     | 37.5075, 127.0355 | 한빛학원(출발·도착지) |

**지도 영역**: 강남·서초 일대, 대각선 약 **1.2km** 범위. 총 경로 거리 약 **1.6km**, 소요 약 **6분 40초**. → 지도가 아주 좁은 영역을 보여준다. 축척·마커 크기를 이 범위에 맞춰
잡을 것.

### 기본 시나리오는 **하원 (DROPOFF)**

노선 이름이 `하원 A노선`이고 학생마다 하차지 주소가 있다. 즉 기본 흐름은 **학원 출발 → 정류장 A (김민준·이서연 하차) → 정류장 B (박도윤 하차)** 이며, 하원이므로 **
`인계완료(HANDOVER)`** 단계가 실제로 쓰인다.

### 다른 버스 (참고 — 기사 앱에는 안 보임)

- **1호차** `서울34나5678` — 기사 미배차. 학생 3명 (최지우·정하율·강서준)이 있지만 **하차지 좌표가 없어** 자동배차에서 제외된다
- **2호차** `서울56다7890` — 다른 학원 (가온에듀) 소속

## 7. ⚠️ 데이터 제약 — 반드시 지킬 것

디자인 단계에서 흔히 넣지만 **이 시스템에는 없는 것들**이다.

| 넣지 말 것                         | 이유                                                             |
|------------------------------------|------------------------------------------------------------------|
| **학생 사진/아바타**               | `Student` 엔티티에 사진 필드가 없다. 이름 이니셜 원형까지가 한계 |
| **학부모 연락처 · 전화 걸기 버튼** | 기사용 API로 내려오지 않는다                                     |
| **학생 개인 위치(실시간)**         | 기사 화면 API에 없다. 지도에는 **버스 위치와 정차 지점**만       |
| **정차별 도착 실적 시각**          | 계획 ETA만 있고 "실제 도착 시각"은 별도로 없다                   |
| **QR/NFC 스캔**                    | 도입하지 않기로 확정됐다. 승하차는 **기사 수동 기록** 뿐이다     |
| **좌석 배치도**                    | 좌석 단위 데이터가 없다(정원 숫자만)                             |
| **주간/월간 통계, 리포트**         | MVP 범위 밖                                                      |
| **채팅·메시지**                    | 없다                                                             |

**반대로 반드시 넣을 것**

| 항목                                    | 이유                                                      |
|-----------------------------------------|-----------------------------------------------------------|
| **`하차`와 `인계완료`를 다른 동작으로** | 안전 요구사항. "내림"과 "보호자에게 넘김"은 다른 사건이다 |
| **운행 종료 차단 상태**                 | 차내 잔류 방지 — 이 앱의 존재 이유 중 하나                |
| **등원/하원 구분**                      | 같은 학생도 방향에 따라 장소·순서가 다르다                |

## 8. ⚠️ 설계 시 알아야 할 흐름 제약

**학생 이름은 "운행 세션을 시작해야" 받을 수 있다.**
노선 API (`stops[]`)는 `studentId`(숫자)만 주고 **이름이 없다.** 이름이 들어 있는 건 운행 세션 명단 (`GET /api/drive-sessions/{sessionId}/roster`)
뿐이고, 이건 `POST /api/drive-sessions/start` 로 운행을 시작한 뒤에야 조회된다.

→ **디자인상 "운행 시작"은 선택 기능이 아니라 필수 관문이다.** 시작하지 않으면 명단에 이름을 띄울 수 없다. 5.2 화면을 건너뛰는 흐름을 만들지 말 것.

## 9. 디자인 시스템 제약

- **Flutter / Material 3** 로 구현한다. M3 컴포넌트로 표현 가능한 범위를 지킨다
- 라이트/다크 모두 필요. 색은 **시드 색 하나에서 파생**된다 (현재 `#2563EB`) — 임의 팔레트를 늘리지 말고 M3 역할색 (primary/surface/error 등)으로 지정할 것
- 간격은 **4의 배수** 스케일: 4 / 8 / 16 / 24 / 32 / 48
- 모서리 반경: 6 / 12 / 20
- 주요 버튼 최소 높이 **48dp**
- 한글 UI. 숫자·시간 표기는 한국식 (`14:05`, `2026. 7. 28.`)
- 지도는 OpenStreetMap 타일 기반 (`flutter_map`) — 지도 스타일 자체는 커스터마이즈 대상이 아니고, **그 위에 얹는 마커·경로선·시트**를 디자인한다
