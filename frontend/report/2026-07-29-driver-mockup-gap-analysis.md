- 일자: 2026-07-29
- 질문: **`기사앱 MVP.dc.html` 대로 기사 화면을 구현할 때, MVP 기능에서 부족하거나 안 맞는 부분이 있는가**
- 대조 대상 3종:
  1. 시안 `frontend/docs/design/source/기사앱 MVP.dc.html` (1,050줄 전체)
  2. API 계약 `backend/docs/MVP_API_SPEC.md` + **컨트롤러 소스 직접 확인**(`@PreAuthorize` 포함)
  3. 현재 구현 `frontend/lib/features/{auth,drivesession,rideevent,routing,location}`
- **실 서버 응답으로 검증**: `http://localhost/api/route-plans/driver/1`, `/api/buses/me` (2026-07-29 실측)
- **코드는 수정하지 않았다.** 보고만 한다.

## A. 백엔드 없이는 안 되는 것

### A1. ⛔ 기사가 볼 수 있는 알림 이력 API가 없다

**시안**: 하단 탭 3개 중 하나가 `알림`이고, 안 읽은 개수 배지까지 붙는다(`기사앱 MVP.dc.html:867-878`). 06번 화면 전체가 알림함이다.

**실제 계약** — 컨트롤러 소스에서 직접 확인:

| 엔드포인트 | 권한 |
|---|---|
| `GET /api/notifications?tenantId=` | `ACADEMY_ADMIN`, `PLATFORM_ADMIN` |
| `GET /api/notifications/children` | `PARENT` |

**`DRIVER`용 조회가 없다.** WebSocket `/user/queue/notifications` 로 실시간 push는 받지만, 그건 **연결돼 있는 동안 오는 것만**이다. 앱을 켜기 전이나 재연결 사이에 발생한 알림은 조회할 방법이 없다.

**왜 중요한가**: 기사가 받는 알림 유형은 근접(`APPROACH`)·**미승차(`NO_SHOW`)**·노선 배포(`ROUTE_PUBLISHED`)다. 특히 미승차는 "도착 10분 뒤"에 발행되는데, 그때 기사가 다른 화면을 보고 있었거나 신호가 끊겼다면 **그 알림은 영원히 못 본다**. 알림함의 존재 이유가 바로 그 복구인데 지금은 복구가 안 된다.

**현재 프론트도 같은 상태다** — `app_routes.dart`의 기사 경로는 `/driver/route`·`/driver/roster` 2개뿐이고 알림 경로는 관리자 전용(`/admin/notifications`)이다. 즉 이건 이식하다 빠뜨린 게 아니라 **처음부터 범위 밖이었다**.

**선택지**
1. **백엔드에 기사용 알림 이력 추가** — `GET /api/notifications/me`(권한 `DRIVER`, 본인에게 push된 것만) 또는 기존 `/api/notifications`에 `DRIVER` 허용 + 서비스 계층에서 본인 대상만 필터. 시안대로 가려면 이게 필요하다.
2. **알림 탭을 MVP에서 뺀다** — 하단 탭 2개(지도·명단)로 두고, 실시간 알림은 스낵바/배너로만 처리. 시안 6번 화면은 다음 버전으로.

> ⚠️ 이건 **MVP 범위 결정**이라 사용자 판단이 필요하다. 나 혼자 정할 문제가 아니다.

### A2. ⛔ 정류장 이름을 기사가 받을 수 없다

**시안**: 지도 마커 라벨 `정류장 A · 2명`(`:284`), 정차 카드 제목 `정류장 A`(`:354`), 명단 그룹 제목 `정류장 A`(`:412`) — **세 곳에서 정류장 이름을 쓴다.**

**실제 계약**

```jsonc
// GET /api/route-plans/driver/{busId} → stops[]
{ "seq": 1, "studentId": 5, "lat": 37.5010, "lng": 127.0275, "etaSeconds": 0 }
//  ↑ 이름이 없다. 좌표와 학생 id 뿐이다.
```

정류장 이름이 있는 곳은 두 군데인데 둘 다 막혀 있다:

| 경로 | 상태 |
|---|---|
| `GET /api/routes/{id}/stops` | **`ACADEMY_ADMIN`·`PLATFORM_ADMIN` 전용** (`RouteController:53,60`) |
| `GET /api/drive-sessions/{id}/roster` → `location` | ✅ `DRIVER` 가능. **단 운행을 시작한 뒤에만** |

**핵심 문제**: 노선 탭(시안 03)은 **운행 시작 전에도 볼 수 있어야 하는 화면**인데(시안의 하단 탭 구조상 그렇다), 그때는 roster가 없어 이름을 못 붙인다. 좌표만 아는 상태로 "정류장 A"를 쓸 수 없다.

**선택지**
1. `stops[]`에 `stopName`(또는 `stopId`)을 **추가** — 가장 깔끔하다. 하원은 정류장이 아니라 주소라 `label` 같은 중립 이름이 낫다
2. `/api/routes/{id}/stops`에 `DRIVER` 허용 — 담당 버스의 노선만
3. **운행 시작 전에는 좌표 기반 표기**(`1번 정차`)로 두고, 시작 후 roster의 `location`으로 이름을 채운다 — 백엔드 무변경. 다만 **같은 화면이 시작 전후로 다르게 보인다**

## B. 클라이언트에서 풀 수 있지만 지금 구현에 없는 것

### B1. 🟡 `stops[]`는 정차가 아니라 **학생** 단위다

**실측** (`GET /api/route-plans/driver/1`, 2026-07-29):

```
direction=PICKUP status=PUBLISHED stops=6
   seq=1 studentId=5  lat=37.5010 lng=127.0275 eta=0
   seq=2 studentId=4  lat=37.5010 lng=127.0275 eta=0
   seq=3 studentId=2  lat=37.5010 lng=127.0275 eta=0
   seq=4 studentId=1  lat=37.5010 lng=127.0275 eta=0     ← 여기까지 전부 같은 좌표
   seq=5 studentId=6  lat=37.5045 lng=127.0310 eta=192
   seq=6 studentId=3  lat=37.5045 lng=127.0310 eta=192
```

**`seq`가 학생 번호다.** 실제 정차는 2곳인데 6줄이 온다.

| | 시안 | 실제 API | 현재 구현 |
|---|---|---|---|
| 지도 마커 | 2개 (`1`, `2`) | — | 6개가 두 좌표에 겹쳐 찍힌다 |
| 정차 카드 | 3장(출발·A·B), `0/2명` | — | **6장**, 각 `학생 #5` |
| "남은 정차" | `2곳` | — | `6곳` |

→ **좌표로 묶는 그룹핑이 반드시 필요하다.** 다행히 같은 좌표는 `etaSeconds`도 같아서(`0,0,0,0 / 192,192`) 그룹당 ETA가 자연스럽게 하나로 떨어진다. `seq`는 그룹의 최솟값을 쓰면 된다.

현재 `route_stop_tile.dart`는 `학생 #${stop.studentId}`를 그대로 찍고 있어 시안과 다르다.

### B2. 🟡 명단의 정차 그룹 + 접기/펼치기

**시안**: 정차별 카드 안에 학생 행이 들어가고, 헤더를 누르면 접힌다(`:406-469`). 25명 시나리오에서 접기가 실질적 기능이다(`g.collapsedSummary`).

**현재**: `driver_roster_screen.dart`는 학생 행을 **평평하게** 나열한다. 정차 개념이 없다.

**가능성**: roster의 `location`(정류장명 또는 하차지 주소)으로 묶을 수 있다. **B1의 그룹핑과 같은 키를 써야** 지도·명단이 어긋나지 않는다.

### B3. 🟡 지도 "내 위치" / "전체 경로" 버튼

시안 `:308-317`에 우하단 플로팅 버튼 2개가 있다. `MapViewAdapter`(`core/map/spec/`)는 현재 **마커·경로선을 그리는 것만** 노출하고 카메라 제어 API가 없다. 포트에 `moveTo(GeoPoint)` / `fitAll()` 정도를 추가해야 한다.

> 포트를 넓히는 일이라 `flutter_map` 지식이 impl 밖으로 새지 않게 주의해야 한다(컨벤션 §5).

### B4. 🟡 하단 탭 3개

시안은 지도·명단·**알림**. 현재는 지도·명단 2개다. **A1이 해결돼야 의미가 있다.**

## C. 데이터 자체가 없는 것

### C1. ⛔ 미승차(`NO_SHOW`) 배지

시안은 학생 행에 `! 미승차` 배지를 붙이고 **행 배경까지 경고색**으로 바꾼다(`:429-431`). 지시서 §5.4도 "미승차 학생은 눈에 띄어야 한다"고 요구한다.

**그런데 명단에도 승하차 기록에도 이 상태가 없다.** 서버는 `NO_SHOW`를 **알림으로만** 발행한다.

- `DriveSessionRosterEntry(studentId, name, location, lat, lng)` — 상태 필드 없음
- `RideEventResponse` — 실제 발생한 승하차만. 미승차는 "일어나지 않은 사건"이라 여기 없다

이미 D7에서 `roster_student_tile.dart:49-54`에 이 사실을 주석으로 남기고 `isNoShow`를 **항상 false**로 두었다. 표기 규칙은 구현돼 있으니 데이터만 생기면 인자만 채우면 된다.

**A1을 해결하면 이것도 같이 풀린다** — 기사 알림 목록에서 `NO_SHOW` 알림의 `studentId`를 뽑아 명단에 겹치면 된다. 두 항목이 같은 뿌리다.

### C2. 🟡 알림 안읽음 개수 배지

서버 `NotificationResponse`에 읽음 상태가 없다. 클라이언트가 "마지막으로 알림 탭을 연 시각" 이후 도착분을 세는 **로컬 근사**만 가능하다. 앱을 재설치하거나 기기를 바꾸면 초기화된다. MVP에서는 이 정도로 충분하다고 본다.

## D. 시안 쪽이 틀린 것 — **구현하면 안 된다**

> 지시서 우선 원칙(`DESIGN_SYSTEM.md` 머리말: *"시안과 지시서가 충돌하면 지시서가 이긴다"*)에 따라, 아래는 시안을 따르지 않는다.

### D1. ❌ 하원 그룹을 "정류장 A / 정류장 B"로 묶었다

시안 스크립트(`:746-754`):

```js
{ seq: '1', title: '정류장 A', kind: 'ALIGHT', kindLabel: '서초구 방면 하차 · 2명', students: stopA },
{ seq: '2', title: '정류장 B', kind: 'ALIGHT', kindLabel: '강남구 방면 하차 · 1명', students: stopB },
```

**하원에서는 학생이 정류장이 아니라 각자의 하차지에서 내린다.** 지시서 §6.5 시드도 김민준 `서울 서초구 자택` · 이서연 `서울 서초구 자택2` · 박도윤 `서울 강남구 자택`로 **셋 다 다른 주소**다. 백엔드도 하원이면 `student.getDropoffAddress()/Lat/Lng`를 쓴다(`DriveSessionQueryService:78-80`).

시안은 **승차 정류장 이름을 하차 그룹에 재사용**했고, "서초구 방면"이라는 상위 분류를 임의로 만들었다. 그런 분류는 API에 없다.

**옳은 처리**: 하원 그룹은 **하차지 좌표로 묶고 제목은 `location`(주소)을 쓴다.** 우연히 같은 좌표면 한 그룹, 아니면 각자 한 그룹이다. "○○구 방면" 같은 라벨은 만들지 않는다.

### D2. ❌ 종료 요약의 "소요 시간"이 계획값이다

시안 종료 화면(`:492-495`)이 `소요 시간 6분 40초`를 보여주는데, 이 값은 노선 계획의 `totalDurationS`(397초)다. **실제 운행 시간이 아니다.**

기사가 종료 화면에서 기대하는 건 "오늘 얼마나 걸렸나"이고, 그건 `DriveSession`의 `startedAt ~ endedAt`이다. 계획값을 실적처럼 보여주면 **매일 똑같은 숫자가 나온다.**

**옳은 처리**: 소요 시간은 세션 기준(현재 `DriveSession.elapsed`가 이미 있다). 총 거리는 계획값밖에 없으므로 `계획 거리`라고 밝히거나 뺀다. 처리 건수는 승하차 기록 수로 계산 가능하다.

### D3. ❌ 로그인 화면의 학원명

시안 `:164`가 `한빛학원 · 운행 기록 앱`을 로그인 **전에** 보여준다. 테넌트는 로그인 후 JWT `memberships`에서야 알 수 있다. 하드코딩하면 다른 학원에서 틀린 이름이 뜬다.

**옳은 처리**: 로그인 전에는 서비스명만(`통학버스 기사`). 학원명은 로그인 후 앱바 부제에 넣는다 — 시안도 `start` 화면 부제를 `박기사 · 한빛학원`으로 두고 있어 그쪽은 맞다.

## E. 확인 결과 문제 없는 것

걱정했다가 소스를 확인해 **아니라고 판명된** 것들이다. 다음 세션이 같은 걱정을 반복하지 않도록 남긴다.

| 항목 | 확인 결과 |
|---|---|
| **새로고침하면 상태가 날아가나?** | ✅ 아니다. `GET /api/ride-events/bus/{busId}?date=`(권한 `DRIVER`, `MVP_API_SPEC.md:317`)가 있고, `DriverRosterController.build()`가 명단 + 그날 기록을 합쳐 상태를 만든다. 앱을 껐다 켜도 복원된다 |
| **운행 종료 차단이 서버에도 있나?** | ✅ 있다. `DriveSessionCommandService.requireNoOnboardStudents()` — 세션 시작 후 마지막 기록이 `BOARD`인 학생이 남으면 종료를 거부한다. 시안의 차단 화면이 서버 계약과 일치한다 |
| **버스 정보(호차·차량번호·정원·배정·노선명)** | ✅ `GET /api/buses/me`에 **전부 있다**(`name`·`plateNumber`·`seatCapacity`·`onboard`·`routeName`). 현재 화면이 `busId`만 쓰는 건 **프론트 미구현일 뿐** — D5 보고에 이미 남겼다. 응답을 세션에 통째로 캐시하면 시안대로 채워진다 |
| **앱바 부제(`3호차 · 하원 A노선 · 2026. 7. 28.`)** | ✅ 위 API + 노선 응답의 `serviceDate`로 전부 만들 수 있다 |
| **낙관적 UI 금지** | ✅ 컨트롤러가 이미 서버 응답 뒤에만 상태를 옮긴다 |
| **정차별 진행률(`0/2명`)·현재 탑승 인원** | ✅ 명단 + 기록으로 계산 가능 |
| **위치 전송 중 표시** | ✅ 구현돼 있다 |
| **25명 스트레스** | ⚠️ 기능 문제는 아니다. 실측 시점 버스 1에 **6명**이 배정돼 있었다(정원 25). 25명 검증이 필요하면 시드를 늘려야 하지 시안·API 문제는 아니다 |

## 권고 — 이 순서로 처리하는 게 낫다

1. **먼저 정할 것 (사용자 판단)**: A1 — **기사 알림함을 MVP에 넣는가.** 넣으면 백엔드에 기사용 알림 이력 API가 필요하고, C1(미승차 배지)도 같이 풀린다. 안 넣으면 하단 탭 2개로 가고 시안 06번 화면은 다음 버전으로 미룬다. **이 결정이 A1·B4·C1 세 항목을 한꺼번에 가른다.**
2. **A2 정류장 이름**: 백엔드에 `stopName`을 넣는 게 정공법이지만, **B1 그룹핑을 먼저 하고 "운행 시작 전에는 `1번 정차`"로 두는 우회**도 실용적이다. 백엔드 변경 없이 시안의 90%가 나온다.
3. **B1 → B2 순서로 그룹핑** — 같은 그룹 키를 지도와 명단이 공유해야 한다. 이게 시안과 현재 구현의 **가장 큰 시각적 차이**다.
4. **D1·D2·D3은 시안을 따르지 않는다** — 고쳐서 구현하고, 그 근거를 `DESIGN_SYSTEM.md`에 한 줄씩 남긴다(§8 "시안에 있어도 구현하지 않는 것"과 같은 성격).
5. B3(지도 카메라)·C2(배지)는 마지막. 없어도 화면이 성립한다.

**추정 규모**: 백엔드를 안 건드리는 범위(B1·B2·B4-일부·D1·D2·D3 + 버스 정보 채우기)만으로도 시안과의 체감 차이는 대부분 사라진다. A1만 별도 결정이 필요하다.
